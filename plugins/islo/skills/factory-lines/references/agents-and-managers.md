# Agents and Managers

An Agent is reusable across Lines. It belongs to one Factory and uses one Machine. Define its Machine, harness, model, prompt, Skills, and MCP servers with the fields supported by the installed `islo schema agent`. Validate before create or update. Attach repository procedures as Skills or keep them in the repository.

Recommend a model from the appropriate live catalog, taking capability, cost, and provider connection into account. Do not assume one catalog works for every harness. Validate the complete Agent configuration with `islo agent validate` before saving it. Job-only `run_agent` fields and sandbox environment variables do not belong in an Agent configuration. The Machine supplies the filesystem, repositories, environment, gateway profile, and lifecycle. An Agent's prompt should say what it owns and what it must return, while Line inputs provide the task-specific context.

List every remote MCP server's host in the blueprint. An Agent's MCP declaration does not by itself authorize network access: configure the Machine's gateway profile with an allow rule for each required host and an appropriate authentication rule. Connect credentials locally; never paste them into an Agent manifest or prompt. Verify a server's connectivity with an approved, read-only request before the Agent depends on it. A provider connection can still be invisible to sandbox-side reads, so use local CLI status for that check.

The built-in Manager is the default for Line routing. Use a prompt Agent Manager when reusable routing behavior or a chosen harness/model is needed. Its Agent has its own Machine; prepare that Machine first. The Agent prompt carries reusable policy. A Line-specific `manager.prompt`, where supported by the installed schema, replaces the reusable prompt for that Line. Do not combine a Manager Agent with legacy `[agent.instructions]`; transition instructions describe individual routing decisions. Check `islo schema factory --short` for the currently supported Manager form.

Two Agent stages in one Line run with the same `sandbox_name` share the Machine-backed filesystem, while retaining separate Agent sessions. Every Agent in the group must reference the same Machine. Choose distinct names for isolation. Do not imply that separate Machines can share one stage workspace or that one session's conversation becomes another's context. Pass semantic outputs explicitly between interactions.
