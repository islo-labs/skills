# Line checklist and bundled examples

Read this before drafting a Line. Then use the local [good Line examples](../lines-good-examples/README.md) and [bad Line examples](../lines-bad-examples/README.md): they contain actual TOMLs, Agent prerequisites, typed contracts, sample stage results, and corrected counterparts. All needed context is bundled; readers do not need access to private tenant Lines. Confirm supported fields with the installed schemas and follow [create-a-line.md](create-a-line.md) for approval and validation.

## Checklist

- **Every stage has a summary.** Declare a required string `summary` output with a short account of the result, evidence, and any blocker, including a successful no-op. A verdict, transcript, or role-specific summary alone does not supply the standard stage summary.
- **Match publication to the Line's final deliverable.** Only when that deliverable is a report or text, require it as a final artifact or Knowledge item, typically **one item for the Line**, not one per Agent. Assign publication to the owning final stage, confirm it succeeded, and return the actual reference. Intermediate Agents can pass draft text and evidence as typed outputs. Update the same item on a retry. PR/comment/action outcomes may have **zero Knowledge items**: existing PR/comment links are valid deliverable references; do not duplicate them as Knowledge reports. See the [final-report and PR/comment examples](../lines-good-examples/README.md#pick-the-final-deliverable-first).
- **Type the handoff.** Keep verdicts in enum strings, PR/evidence references in string arrays, and any final Knowledge slug in a string. Declare matching inputs on consuming stages and use `type = "output"` bindings. Do not recover IDs or decisions by parsing a summary.
- **Choose the event and its scope.** Start manual while testing; use schedules with an explicit timezone or the catalog's provider event for approved automation. In Linear, a label-only request uses selected scope, not all scope with a labels list. Verify inclusion and exclusion with the [bundled label-only example](../lines-good-examples/labeled-comment.line.toml) and [trigger semantics](triggers.md#linear-label-only-selection).
- **Route and bound the work.** Use Agent stages, explicit success/revision/blocked outcomes, and appropriate iteration/time/budget limits. Agree an explicit spend cap with the requester based on stages, expected costs and retries; do not blindly copy $5, infer a universal default, remove cost guards, or substitute a universal larger cap. See the [$5-cap anti-example and workload-based correction](../lines-bad-examples/README.md#choose-a-workload-budget). Define what the Manager should do when evidence or a required final publication is unavailable. Shared sandbox groups require the same Machine.
- **Verify the promised result.** Inspect every stage's summary and typed handoffs, then check the Line's actual final deliverable: a published report reference, PR URLs, comment links, or the requested action evidence. A provider/model failure is a limitation to report, not evidence that a result exists. Use local trigger fixtures first; live provider tests need approved effects.

The [good folder](../lines-good-examples/README.md) is for schema-checked positive examples. The [bad folder](../lines-bad-examples/README.md) contains intentional anti-examples that can be schema-valid but wrong; never deploy them. The example validator identifies and parses those separately, without treating them as successful deployment examples.

For report publication commands, see [Knowledge surfaces](../../surfaces/references/knowledge.md#publish-a-markdown-document).
